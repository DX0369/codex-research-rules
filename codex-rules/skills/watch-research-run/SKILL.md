# 托管长时间科研任务

## 启动与登记

1. 使用 `prepare-research-run` 核对本轮授权、正式入口、协议、输入输出和资源。复用项目 `tmp/<任务标识>/PLAN.md`，写明预期结果、验收方法、结果分析和必要路径。用户明确授权工程恢复时，按阶段记下可做的修复、恢复方式和已确认的资源、时间及次数限制。已获授权且未指定次数时，每个阶段最多 3 次正式恢复尝试。以恢复该阶段而提交或启动的正式任务计数，每次尝试只记一次。因上游失败而取消、尚未启动的依赖作业随上游一并记录。原会话的用户指示决定授权范围。
2. 在目标 Linux 的当前会话执行 `python3 <本技能的 scripts/watch.py 的绝对路径> probe`。Python 需要 3.8 或更新版本。脚本从 `CODEX_THREAD_ID` 识别原会话，从实际 `CODEX_HOME` 找官方后台的 Unix socket，并使用已安装的 Codex CLI。收到匹配 ID 的 `idle` 或 `active` 即可登记自动唤醒。已有自定义后台时，用 `--socket` 和必要的 `--codex` 指定实际入口。用户要求自动唤醒且探测失败时，在正式启动前说明原因，确认改用可接续的聊天或由用户接受记录模式。仅记录终态时使用 `--record-only`。遇到控制 socket 权限错误时，核对当前执行权限与实际个人路径，按本轮授权使用可访问该 socket 的入口。
3. 每次尝试使用计划目录下独立的 `watch/<尝试标识>/`。在能脱离当前终端的原有机制中运行脚本，并用绝对路径登记脚本、计划和状态目录。外层启动器会清理环境时，按探测结果显式传递 `--thread` 和连接参数。任务运行环境、命令与正式输出位置沿用原计划。

首次接入优先使用桌面 App 的官方 SSH 连接或服务器上的官方 Codex 后台。登录环境提供个人 `CODEX_HOME`、可用 CLI、认证和模型网络。接入共享后台的 VS Code 面板使用同一探测流程。接入后重开窗口沿用已有连接。当前面板使用独立后台时，以 `probe` 结果判断是否能自动投递。对依赖本机转发的主机，可为托管命令传入 `--model-url` 和实际提供商的 HTTPS 地址，让监控沿用启动环境的代理，在模型网络恢复后投递。

### VS Code 面板实时显示

首次接入或连接方式改变后，用真实聊天验证。等待作业退出，核对原会话收到事件并完成回复。验证关闭客户端时，在重开前从服务器确认回复已经生成。VS Code 实时显示以实际面板为准。测试应用级启动配置时，使用独立的 VS Code 用户数据目录及远端测试 `CODEX_HOME`。

## 监控入口

按这次任务的实际启动方式选择入口。同一台机器可同时运行调度任务和普通进程。

- **Slurm 作业。** 先完成会话探测，再按授权提交。拿到确切 job ID 后，用原有后台机制运行 `slurm` 子命令，借助 `squeue` 与 `sacct` 获取真实终态。接手已提交作业也使用这一入口。若监控中断且仍缺少终态，可对同一 job 和状态目录重新启动监控。数组或多阶段运行按计划登记所需的具体作业，完成时核对全部预期阶段。按需用 `--wait-limit` 限定等待。
- **普通 Linux 进程。** 用 `run` 包住实际任务命令，由它等待子进程并记录退出码。外层根据现场可用能力继续使用 `screen`、`nohup`、`setsid` 或 `systemd-run --user`。用户级 systemd 需有可访问的用户服务管理器。只有 `nohup` 或 `setsid` 可用时，选可用的一种即可。项目 launcher 必须等实际工作结束，并把失败传播为非零退出状态。保留项目原有日志重定向和环境。使用管道时核对任务的真实退出状态。已经在跑且缺少终态记录的任务，依据日志和产物审计，证据不足时标记未知。

```bash
python3 "$watch_script" slurm --plan "$plan_file" --state-dir "$attempt_dir" --job-id "$job_id"

watch_run=(python3 "$watch_script" run --plan "$plan_file" --state-dir "$attempt_dir" -- "${task_argv[@]}")
nohup "${watch_run[@]}" >"$watch_log" 2>&1 </dev/null &
```

`task_argv` 是原任务的命令与参数。使用其他后台机制时，将同一个 `"${watch_run[@]}"` 交给原启动入口。

确认 `watch.json` 出现、实际作业存在，报告作业或进程标识和状态目录。当前轮可以结束。脚本先在 `event.json` 保存终态，再投递。`delivery.json` 的 `queued` 表示已入队，`received.json` 表示原会话已接手。后台暂不可用时，脚本可启动已登记的官方后台，并在默认 24 小时内逐步放慢频率重试。重试到期后可用 `deliver --state-dir <目录>` 继续投递。遇到 `uncertain` 或 `sending` 时先查记录，避免重复触发。包装器异常消失且缺少终态时，先审计实际作业。

## 原会话收到事件

1. 执行通知中的 `ack`，它核对 `CODEX_THREAD_ID` 和该次事件标识。读取登记的计划和终态证据，检查最新用户指示以及真实作业状态。若 `first_ack` 为 `false`，先检查前一轮已做事项。只读权限或其他原因导致回执写入失败时，继续只读核对并说明原因，自动恢复须等回执能写入。
2. 先用 `audit-experiment-status` 核对实际退出和产物。队列接受通知、进程退出、验收完成分别报告。Slurm 辅助步骤异常时，核对主批处理、计划要求的步骤和预期产物，再判断是否需要恢复。人工取消、未确认终态或原作业仍活跃时，记录证据与后续判断。
3. **工程故障。** 定位最早能够解释失败的证据。核对工程恢复授权、原运行终态和阶段剩余预算。由 `prepare-research-run` 复用实际入口验证针对故障的修复，确认实验协议、可比性和资源门槛仍满足后恢复。同一故障复发时，先查修复是否生效，有新证据支持恢复再提交。有有效存档时按项目约定续跑。仅后处理未完成时，在授权范围内优先补该阶段。提交前在计划中核对次数并登记新尝试。重跑使用独立正式输出目录，保留旧证据并为新尝试登记独立监控。超出授权或证据不足时报告现状与选项。
4. **协议或结论可能受影响。** 解释已知原因、拟改动及对可比性的影响，等用户确认后恢复。数据版本、划分、指标、训练参数和失败处理遵循已确认协议。
5. **进程以零退出码结束。** 按计划核对输出、样本覆盖和失败记录。覆盖不足时记录部分完成及缺项，验收通过后报告完成。依据已有结果给出证据支持的结论与下一步。正式重算或新实验按本次授权执行。有实质进展时按项目规则更新 `PROJECT_STATE.md`，本轮结束且投递记录已落盘后，清理已无续接用途的临时计划和监控记录。
