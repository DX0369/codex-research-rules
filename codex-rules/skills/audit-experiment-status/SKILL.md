# 审计实验状态

## 原则

- 全程只读。不得启动、停止、恢复、补跑或杀死进程，不得修改文档、代码和实验产物。
- 只报告可由当前证据支持的状态。不得把 PID、目录、日志或完成标记中的任一项单独视为完成。
- 区分文档记录、磁盘事实、当前运行事实、冲突和未知信息。
- 只检查用户指定的实验；未指定时，以 `PROJECT_STATE.md` 记录的当前实验和实际活跃任务为范围。
- 若存在多个无法安全区分的候选实验，先报告候选项并询问，不猜测目标。

## 审计流程

1. 读取项目根目录下已有的 `PROJECT.md` 和 `PROJECT_STATE.md`，提取实验标识、环境、机器、
   GPU、输出位置、预期任务和完成条件。文档缺失时记录为未知，不创建文档。
2. 检查与目标实验直接相关的进程或调度任务，区分 launcher、worker 和已经退出但残留的 PID
   文件。不得把搜索命令自身算作目标进程。
3. 在可用时检查 GPU 进程和利用率，并核对 PID、命令、GPU 和实验标识是否一致。GPU 空闲
   不足以单独证明失败，GPU 忙也不足以证明目标实验正常。
4. 先检查日志大小和更新时间，再读取尾部并定向搜索错误、完成信息、进度和样本标识；不得
   整体输出大型日志。
5. 从已确认的计划列出预期实验条件，核对哪些整组缺失，再按真实样本身份检查每组的覆盖、重复、漏项和失败。分别核对计算、保存或导出、收尾和后续评测。统一使用已有记录作为审计证据。
6. 对照新旧评分器时，先核对题目身份、失败样本处理和旧评分口径，用已保存结果校对旧分。记录对不上的位置和可比范围。需要重新计算正式指标时，按本轮正式运行授权处理。
7. 根据各阶段证据判定状态，同时说明科研假设是否达到约定门槛。证据不足时标为未知。

## 状态定义

- `running`：存在与目标一致的活跃计算，并有日志、输出或调度状态持续推进的证据。
- `partial`：只完成部分预期工作，或部分任务成功而其他任务未完成；不得表述为正式完成。
- `failed`：存在明确错误、异常退出或失败任务，且当前没有对应工作继续有效运行。
- `completed`：预期任务全部结束，覆盖符合协议，失败与重复记录已核对，并有成功退出或等价
  的完成证据。
- `unknown`：现有证据不足、相互冲突或无法对应到同一实验。

## 输出

使用中文简要报告：

1. 审计时间、目标和范围；
2. 每个实验或任务的状态及关键证据；
3. 文档记录与实际状态的冲突；
4. 未知信息和无法确认的原因；
5. 待处理任务，但不自动执行。

若用户同时明确要求更新 `PROJECT_STATE.md`，先完成只读审计，再使用
`update-research-project-state` Skill 写入已经确认的事实。
